# ТЗ: Двухступенчатый Differenz-НДС для партнёрских авто (правки-2)

> **Статус: реализовано 06.08.2026** (коммиты «правки-2 Э1…Э5»). Э1 — ядро и тесты,
> Э2 — форма с автонаценкой и live-расчётом, Э3 — карточка, Э4 — снапшот и списки,
> Э5 — проверки. Открытые вопросы к бухгалтеру — в `docs/BACKLOG-MVP.md`.

Самодостаточное задание для разработки в проекте MOTORHOF CRM. Перед началом прочитай
`CLAUDE.md` и `AGENTS.md` в корне проекта — там обязательные конвенции. Это ТЗ имеет
приоритет над старой логикой, описанной в CLAUDE.md, в части расчёта НДС и маржи
партнёрских авто.

---

## 1. Бизнес-контекст (зачем)

Часть автомобилей закупается партнёрской компанией **e.U.** (владелец в системе —
любой партнёрский: `MRIYA_MOTORS`, `A_MOTORS`, `AUTOHUB`; проверка — хелпер
`isPartnerOwner()` из `src/lib/format.ts`), а продаётся конечному клиенту основной
компанией **OG** (`MOTORHOF_OG`). Юридически происходят **две продажи**:

1. **Ступень 1:** e.U. продаёт авто OG по «внутреннему счёту» с наценкой
   (поле `fictitiousMarkup` в модели Car — уже существует). Наценка — официальный
   заработок e.U., чтобы у налоговой не было вопросов о продажах без прибыли.
   С этой продажи e.U. платит свой Differenz-НДС.
2. **Ступень 2:** OG продаёт клиенту и платит свой Differenz-НДС, где базой
   закупки является **передаточная цена** из ступени 1 (не исходная закупка!).

Экономика в CRM при этом **сквозная по группе**: одна общая маржа, «моё/твоё»
между компаниями НЕ разделяем. Наценка в марже группы не участвует (деньги
перетекают внутри группы), она влияет на маржу только через размер НДС.

Сейчас система считает только одну ступень НДС — это надо заменить для
партнёрских авто. Для авто владельца `MOTORHOF_OG` ничего не меняется.

## 2. Формулы (единственный источник истины)

Все расчёты — только в `src/lib/finance.ts` (Prisma `Decimal`, округление half-up
до цента — так уже сделано в файле). В компонентах денежной арифметики быть не
должно (исключение — существующий live-препросмотр в форме на JS-числах,
см. §4.2).

Применимость: владелец — партнёрский **И** налоговая схема
`DIFFERENZBESTEUERUNG`. Все остальные комбинации (владелец `MOTORHOF_OG`;
схема `REGELBESTEUERUNG` у любого владельца) считаются по текущей логике
без изменений.

### Входные величины

| Обозначение | Откуда |
|---|---|
| `realCost` — реальная закупка | PRIVAT/HAENDLER: `purchasePrice`; AUKTION: `auctionInvoiceTotal + auctionTransportCost` |
| `vehicleBase` — стоимость автомобиля | AUKTION: `auctionVehiclePrice`; PRIVAT/HAENDLER: `purchasePrice` |
| `markup` | `fictitiousMarkup` |
| `saleGross` — цена продажи клиенту | плановая `plannedSalePriceGross` (или фактическая при продаже) |
| `expenses` | сумма APPROVED-расходов по авто (как сейчас) |

### Расчёт

```
finalPurchase  = realCost + markup                     // «финальная закупочная», как сейчас
stage1Base     = finalPurchase − vehicleBase           // база НДС e.U.
vatEU          = stage1Base × 0.20                     // Дифф. НДС e.U. (ступень 1)
transferPrice  = finalPurchase + vatEU                 // передаточная цена (счёт e.U. → OG)
vatOG          = max(0, saleGross − transferPrice) × 0.20   // Дифф. НДС OG (ступень 2)
vatTotal       = vatEU + vatOG
margin         = saleGross − vatTotal − realCost − expenses // маржа ГРУППЫ, одна
```

Обрати внимание:
- в марже вычитается `realCost` (без наценки), а не `finalPurchase`;
- база ступени 2 — `transferPrice`, а НЕ `auctionVehiclePrice` (текущая
  логика для аукциона меняется — только для партнёрских авто);
- НДС e.U. не зависит от цены продажи — он фиксируется закупкой и наценкой.

### Автоматическая наценка

```
suggestedMarkup(realCost) = max(250, ceilTo10(realCost × 0.05))
// ceilTo10 — округление ВВЕРХ до кратного € 10
```

Константы (ставка 5%, пол € 250, шаг округления) вынести в именованные
константы в `finance.ts` — их будут менять.

Поле остаётся редактируемым: авторасчёт — значение по умолчанию, пользователь
может ввести своё (§4.2).

### Контрольные примеры (обязательные тест-кейсы)

**Кейс A — Fiat 500, Аукцион:** invoiceTotal 2740.00, vehiclePrice 2272.00,
transport 186.65, markup 300, расходы 750.
- finalPurchase = 3226.65; stage1Base = 954.65; **vatEU = 190.93**;
  **transferPrice = 3417.58**
- saleGross 4990 → vatOG = 314.48; vatTotal = 505.41; **margin = 807.94**
- saleGross 5490 → vatOG = 414.48; margin = 1207.94
- saleGross 4490 → vatOG = 214.48; margin = 407.94
- suggestedMarkup(2926.65) = **250** (5% = 146.33 < пола)

**Кейс B — Аукцион без транспорта:** invoiceTotal 5596.00, vehiclePrice 5099.00,
transport 0, markup 300, расходы 500.
- finalPurchase = 5896.00; **vatEU = 159.40**; **transferPrice = 6055.40**
- saleGross 9290 → vatOG = 646.92; vatTotal = 806.32; **margin = 2387.68**
- saleGross 8590 → vatOG = 506.92; margin = 1827.68
- suggestedMarkup(5596.00) = **280** (5% = 279.80 → вверх до 10)

**Кейс C — Приват:** purchasePrice 10000, markup 500, расходы 0, продажа 13000.
- finalPurchase = 10500; stage1Base = 500; vatEU = 100.00;
  transferPrice = 10600; vatOG = 480.00; vatTotal = 580.00; margin = 2420.00

**Кейс D — не партнёр (MOTORHOF_OG), Аукцион** — текущая логика без изменений:
одна ступень, база НДС = `auctionVehiclePrice`.

**Кейс E — партнёр + REGELBESTEUERUNG** — текущая логика без изменений.

Инвариант для property-теста (по желанию): `vatEU + vatOG` при
`saleGross ≥ transferPrice` равно `(saleGross − vehicleBase) × 0.2 − 0.2 × vatEU`
(каскадный эффект).

## 3. Что уже есть в системе (не ломать)

- `fictitiousMarkup` — поле Car, вводится в `src/components/car-pricing-block.tsx`
  только для партнёрских владельцев. Новых полей в БД **не нужно, миграций нет**.
- `computePricing()` в `finance.ts` + адаптеры `carPricing()/carPricingAt()/
  carMargin()/carFinalPurchase()` в `format.ts` — точка входа всех страниц.
  Расширяй `PricingResult` новыми полями (`vatEU`, `vatOG`, `vatTotal`,
  `transferPrice`, `realCost`), не создавай параллельных функций.
- Redaction — server-side, через `can()`/`viewerFlags()`:
  - `see.internalPrice` (ADMIN/PARTNER) — наценка, ступени НДС, передаточная;
  - `see.acquisition` — закупочные детали; `see.margin` — маржа.
  Роли без `see.internalPrice` видят как сейчас: одну закупочную, один НДС
  (показывать `vatTotal`), одну маржу. Цифр ступеней в их HTML быть не должно.
- Снапшот продажи `buildSaleSnapshot` → `Sale.financialSnapshot` (Json) —
  замораживает маржу при продаже. Исторические снапшоты НЕ пересчитывать.
- Vitest: `src/lib/finance.test.ts` — дополняй, не удаляй существующие кейсы
  (кроме тех, что прямо противоречат новой логике партнёрских авто — их поправь
  под новые формулы с комментарием).

## 4. Этапы работ

Работать поэтапно, после каждого этапа — коммит (сообщение на русском:
`правки-2 ЭN: …`).

### Э1 — Ядро
`finance.ts`: двухступенчатый расчёт по §2 внутри `computePricing()` (партнёр +
Differenz), `suggestedMarkup()`, константы. `format.ts`: прокинуть новые поля
результата. Тесты: кейсы A–E зелёные.

### Э2 — Форма авто (создание и редактирование)
`car-pricing-block.tsx`:
- Поле «Фиктивная наценка»: автозаполняется `suggestedMarkup` от введённых
  закупочных полей. Пока пользователь не правил его руками — пересчитывается
  live при изменении закупки; после ручного ввода — больше не перетирать
  (dirty-флаг в состоянии). Рядом с полем подпись-хинт: «авто: 5% от закупки,
  мин. € 250» и кнопка «↺ авто» для возврата к расчётному значению.
- Live-препросмотр (JS-числа, только отображение — сервер пересчитает сам)
  для партнёрских владельцев показывает строки: Дифф. НДС e.U., Передаточная
  цена (счёт e.U.→OG), Дифф. НДС OG, НДС всего, Маржа группы (план).
  Для MOTORHOF_OG — текущий вид без изменений.

### Э3 — Карточка авто
`src/app/cars/[id]/page.tsx`, блок «Экономика», партнёрское авто + viewer с
`see.internalPrice`:

```
Реальная закупка        € …
Расходы                 € …
План продажи            € …
────────────────────────────
Дифф. НДС · ступень e.U.  € …
Дифф. НДС · ступень OG    € …
НДС всего                 € …
────────────────────────────
Плановая маржа            € …      ← одна, общая
Справочно: внутренний счёт e.U. → OG = € …  (+ наценка € … в подписи)
```

Без `see.internalPrice` — текущий вид (одна закупочная = finalPurchase,
НДС = vatTotal, маржа). Блок «Закупка · Аукцион» оставить, он про ступень 0.

### Э4 — Продажа и метрики
- `buildSaleSnapshot`: добавить в Json `vatEU`, `vatOG`, `transferPrice`,
  `realCost`; `finalMargin` — по новой формуле. Старые снапшоты читаются как
  раньше (поля опциональны при чтении).
- Проверить, что дашборд, список авто, «Продано за месяц», страница клиента
  берут маржу/НДС только через `carPricing`/снапшот (менять их код не должно
  понадобиться — если где-то арифметика захардкожена, вынести в finance.ts).
- Колонка «Закупка» в списке `/cars` для партнёрских авто показывает
  `realCost` (реальную закупку), не передаточную.

### Э5 — Проверка и деплой
```bash
export PATH="$HOME/.local/node/bin:$PATH"
npx tsc --noEmit && npm run lint && npm test && npm run build
```
Плюс ручная проверка в браузере (dev-сервер :3000): форма нового авто
(аукцион + партнёр — live-цифры совпадают с кейсом A), карточка существующего
партнёрского авто, карточка MOTORHOF-авто (не изменилась), вид под ролью без
`see.internalPrice` (ступеней в HTML нет — проверить curl'ом исходник).
Скриншоты формы и карточки. Деплой — только после явного одобрения владельца
(push в `main` запускает Vercel).

## 5. Запреты и грабли

- НЕ обновлять Prisma до v7. НЕ использовать `db push` (миграции тут и не нужны).
- Деньги — только `Prisma.Decimal` в серверном коде; JS-float допустим
  исключительно в live-препросмотре формы.
- Никаких проверок `if (role === …)` — только капабилити.
- Новые CSS-классы — только внутри `@layer base/components` (Tailwind v4,
  см. CLAUDE.md — вне слоя класс молча ломает утилиты).
- Формы — существующий паттерн `useActionState`; после мутаций `revalidatePath`.
- Исторические `financialSnapshot` не трогать и не пересчитывать.
- Ставку 20% не хардкодить по коду — в `finance.ts` уже есть константа ставки,
  использовать её.

## 6. Критерии приёмки

1. Все тесты §2 (кейсы A–E) проходят; `tsc`, `lint`, `build` чистые.
2. На форме аукционного партнёрского авто с цифрами кейса A live-блок
   показывает 190,93 / 3 417,58 / 314,48 / 505,41 / 807,94 при плане 4 990.
3. Наценка автозаполняется (кейс A → 250, кейс B → 280), ручной ввод
   не перетирается, «↺ авто» возвращает расчёт.
4. Карточка партнёрского авто показывает две ступени НДС и одну маржу группы;
   в HTML роли без `see.internalPrice` строк ступеней и наценки нет.
5. Карточки и метрики MOTORHOF-авто не изменились ни на цент.
6. Продажа партнёрского авто замораживает в снапшоте обе ступени; старые
   продажи отображаются как раньше.
