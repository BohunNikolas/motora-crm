# BACKLOG — доработки после MVP

Проект сейчас на стадии **MVP**. Здесь копится всё, что сознательно упрощено или отложено,
чтобы не потерять при доведении до продакшн-уровня. Каждый пункт: что отложено, где, почему,
и что нужно сделать. При закрытии пункта — убирать отсюда со ссылкой на коммит.

Правило: как только что-то откладывается «на потом» — оно попадает СЮДА в тот же момент.

## Расходы (§14, фаза 4a)

- **Вложения к расходу (§14.1 `attachment/files`).** Сейчас у Expense нет файлов (сканы счетов
  нельзя прикрепить). Модель `CarFile` есть только у авто. Нужно: расширить хранилище файлов на
  Expense (по образцу `CarFile` → R2 через `src/lib/storage.ts`, отдача через `/api/files` с
  правами), UI загрузки в форме расхода. Отложено 26.07 по решению пользователя — базовый учёт
  расходов работает без вложений.
- **Экспорт в Excel (§14.3).** Реализован только CSV (`/api/expenses/export`). ТЗ упоминает
  «CSV/Excel». Excel (xlsx) — потом, если понадобится команде.

## UX и производительность (§23, фаза 5e)

- **Server-side пагинация запросов.** Пагинация (`Pagination`) добавлена к спискам
  cars/expenses/clients/warranty, но данные грузятся целиком и режутся в памяти
  (`slice`) — в DOM попадает только страница. При большом объёме нужен реальный
  `skip`/`take` в запросе. Мешает то, что поиск по кириллице идёт в JS (Postgres
  `mode:insensitive` частично закрывает — можно перенести поиск в SQL).
- **Пагинация страницы задач.** `/tasks` использует срезы/группировку, пагинацию
  туда не добавляли — при росте числа задач добавить.
- **Уведомление после сохранения (toast).** §23 просит понятное уведомление после
  сохранения; сейчас — redirect без тоста. Нужен toast-компонент. (Pending-состояние
  кнопок уже сделано — `SubmitButton`/`ConfirmButton` через useFormStatus, коммит 2202566.)
- **Формы не теряют данные при ошибке backend + предупреждение о несохранённых
  изменениях (§23).** Server Action при ошибке (конфликт/права) роняет форму на
  error boundary; нужен `useActionState` с возвратом ошибки и сохранением ввода,
  плюс beforeunload-предупреждение.

## Дашборд (§5, фаза 5d)

- **Разбивка стоимости активного склада по владельцу (§5.2).** KPI «Активный склад»
  показывает общую себестоимость непроданных; §5.2 просит уметь раскрывать/фильтровать
  сумму по владельцу (Mriya Motors / A Motors / AutoHub / MOTORHOF OG). Сейчас — только
  общая сумма.
- **«Расходы за месяц» считаются по invoiceDate.** Расходы без даты счёта (у сид-данных
  invoiceDate пустой) в KPI не попадают — показывает € 0. Это по §5.2 (счета с invoiceDate
  в текущем месяце), но стоит проверить на реальных данных, что менеджеры заполняют дату.

## Календарь (§16, фаза 4c)

- **Строгая обработка Europe/Vienna при вводе.** `datetime-local` в форме термина
  трактуется относительно пояса сервера, а показ времени — через `Intl` с
  `Europe/Vienna`. На локали (Mac в местном поясе) согласовано; на проде (Netlify UTC)
  введённое время сохранится со сдвигом относительно Вены. Нужно: конвертировать
  ввод Vienna→UTC при сохранении (напр. `@date-fns/tz` или `Temporal`). Показ уже
  корректен (viennaDayKey/fmtTime через Intl).
- **UX ошибки конфликта интервалов (§16.3).** Server-side проверка есть и блокирует
  (throw Error с текстом конфликта). Показывается через дефолтный механизм Next
  (как все throw в проекте — `requireCan` и т.п.). Нужно: inline-сообщение в форме
  (useActionState / error.tsx) — общее улучшение для всех форм проекта.
- **Клиентский предчек конфликта (§16.3 «повторять в UI до сохранения»).** Сейчас
  только server-side. Добавить лёгкую проверку на клиенте до отправки.
- **Доставка напоминаний.** `reminderMinutesBefore` хранится, но напоминания
  ниоткуда не отправляются. §16.3 явно разрешает не обещать SMS/email — при
  необходимости сделать in-app уведомления.

## Общие технические долги

- **Проверка на проде отдельных сценариев.** Часть функционала (загрузка/отдача файлов R2)
  проверялась только на проде, т.к. локально R2 недоступен из-за блокировки провайдера. При
  переезде на аккаунты компании (фаза Б) — перепроверить.
- **Prisma Decimal в клиентские компоненты (dev-warning).** Форма авто (`CarForm`,
  `"use client"`) принимает целиком объект `Car` из серверной страницы, а Decimal-поля
  не сериализуются как plain object — в dev Next пишет «Only plain objects can be passed
  to Client Components». Работает, но правильнее передавать уже подготовленные строки
  (как в `CarPricingBlock` через `defaults`). Отложено 03.08.2026 при правке стилей.
- **Адаптив: мобильные представления таблиц.** Широкие таблицы (авто, расходы,
  клиенты, гарантия, настройки) на телефоне листаются горизонтально. Полноценный
  мобильный вид — карточки вместо строк — отложен как отдельная UI-задача.
